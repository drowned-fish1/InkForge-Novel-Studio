# InkForge 小说工作台竞品对比与功能缺口

2026-10-12 状态更新：本文保留首轮调研基线。选区对话附件、旧稿迁移、整书矩阵、每日模板／存稿与 AI 人物卡已经实现，不再按下面的历史表格重复列为缺口。当前下一轮清单见 [下一轮功能缺口与复用建议](./novel-workbench-next-round-2026-10-12.md)。

调研日期：2026-10-11。项目基线：当前工作区文件，包含尚未提交的功能；不只依据 README 或 RC 路线图。

方法：检索产品官网与官方帮助文档，并交叉阅读 InkForge 的用户指南、前端入口、数据模型与主进程服务。竞品能力为公开文档确认，未登录逐一实测；本项目结论为代码与文档审查，未在本轮重新运行应用。表中“未见”指审查范围内未找到完整入口，不等于证明仓库不存在任何相关代码。

## 核心判断

InkForge 已经有较完整的长篇创作基础：人工写作、故事资料、规划、检索记忆、生成、修订、备份、导出都存在。下一阶段的主要机会是把已有能力接到作者的日常操作中，降低切页、重复输入和配置成本。

建议定位为：**面向中文长篇作者、本地保存作品、可自由选择模型、能审阅和回滚 AI 修改的小说工作台。**

这与项目现有范围一致。账号、平台云同步、团队协作、投稿社区属于另一个产品方向，不能因为竞品有就直接当作待补功能。参见 [scope.md](./scope.md)。

## 建议的首批实施范围

第一批围绕两个真实流程交付：

1. **改一段正文**：选区 → 选择润色/扩写/压缩 → 确认相关资料 → 看候选差异 → 接受/重试/撤销。沿用当前写入提案和版本检查，不建立第二套修改机制。
2. **继续写下一章**：留在写作台 → 查看前章与角色资料 → 编辑章节/场景目标 → 看本轮上下文 → 生成并审阅。先接通现有能力，再增加分析视图。

随后做旧稿迁移和新书引导，最后补全书矩阵、写作目标与存稿记录。这样每一批都能被真实作者用完整任务验收。

相对工作量仅是静态判断：只读参考窗和字段编辑为中等；选区提案、迁移导入、上下文解释为中到较大；持久场景片段、系列共享为较大。没有给出未经设计或测量的工期。

## 保留和验证现有优势

本地文件、无账号非 AI 流程、模型分工、自定义书内资料、来源验证、历史状态和修改回滚值得继续作为产品中心。不能因为竞品也有资料库就认定 InkForge 已形成质量优势。

下一阶段应采集本地、可由作者查看的结果：首次有效写作所需步骤、查资料切页次数、AI 候选接受率、重生成次数、接受后再次修改量、每千字 Token/费用、前后事实冲突数量。不要求接入云遥测；先用真实作者测试和本地记录验证。

`QualityService` 当前包含规则统计和经验阈值，质量总分适合作为检查辅助。写得好不好还需要作者评价，避免用总分宣称故事质量提升。`scripts/compare-writer.mjs` 已能比较模型输出与成本；可在它的基础上补充作者评审记录，而不是再建一套对比工具。

## 暂不扩大的方向

- 账号、会员、团队协作、平台云同步：现有范围明确排除，只有产品定位改变时才重新评估。
- 投稿交易与社区：可以先提供本地发布记录和稿件导出。
- 小说转漫剧/视频：竞品中存在，但会引入独立的剧本、分镜和媒体生产链路。
- 更多 Agent 角色：当前已有多 Agent；优先测量它们是否减少返工、改善一致性。
- “百万字绝不失忆”“一键精品”等未经验证的质量承诺：功能存在不等于长篇质量已被证实。
