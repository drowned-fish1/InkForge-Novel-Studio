# Chat Agent

InkForge exposes the novel project to the configured model through a small, auditable tool set. The renderer never receives API keys or filesystem access.

## Request flow

```text
Chat panel
  -> preload IPC bridge
  -> ChatAgentService
  -> OpenAI-compatible streaming tools/tool_calls loop
  -> live text and tool-state events
  -> read-only project services
  -> structured chapter or data proposal
  -> per-block author confirmation
  -> version check + history snapshot
  -> atomic project write
```

Conversations are stored per chapter under:

```text
.inkforge/agents/chat/<chapter-id>.json
```

Each run also writes an inspectable trace containing model turns, tool calls, latency, Token usage, context-budget metrics and failure details:

```text
.inkforge/agents/traces/<chapter-id>.json
```

The trace panel can replay a previous user request. Replays create a new trace and preserve the original trace id as `replayOf`.

## Plan mode and session controls

The composer supports two execution modes:

- **Direct** can read project context and call the tools allowed by the author.
- **Plan** is a one-turn, tool-free pass that produces a numbered execution plan. Tools remain disabled until the author clicks **Execute this plan**.

The Agent panel also exposes per-request controls for automatic-context Token budget, long-term memory, semantic retrieval, pinned or excluded sources, maximum model turns, maximum tool calls, total Token budget and an explicit tool allow-list. An empty allow-list disables every tool.

Each chapter conversation can be forked into persistent branches. A branch inherits messages only through its fork point, so later main-thread messages do not leak into it. Useful assistant replies can be favorited, and common writing tasks can be inserted from prompt templates.

Provider-supplied `reasoning_content` and tool results are kept separate from the visible answer. Both are collapsed by default in the conversation and run trace, while normal Markdown remains rendered as author-facing content.

Pending text and data proposals can be approved as one batch. The batch keeps manually rejected patch blocks rejected, accepts undecided blocks, and then writes the remaining approved changes. Proposal decisions preserve the current chat scroll position instead of forcing the author back to the newest message.

Rollback always opens a confirmation dialog before restoring the pre-write snapshot. **AI YOLO** is an opt-in session mode with its own warning dialog: it auto-applies only proposals newly generated by the current model run, never older pending proposals. Tool allow-lists and run budgets still apply, and Plan mode remains tool-free.

## Model tools

- `get_chapter_context`: reads the chapter plan and recent or full chapter text.
- `get_chapter_memory`: reads current and previous chapter memories.
- `get_story_bible`: reads selected character, world, timeline, clue and term records.
- `inspect_continuity`: runs local consistency checks.
- `search_project`: searches outline, character and world records.
- `semantic_search`: runs local vector retrieval across chapters, memories, characters, world entries, clues, terms and timeline events.
- `propose_chapter_edit`: creates an append or replace proposal.
- `propose_chapter_patch`: creates exact-anchor patch blocks that can be accepted independently.
- `propose_scene_plan`: proposes project-backed scene plans.
- `propose_character_update`: proposes a character state or profile update.
- `propose_clue_update`: proposes a foreshadowing update.
- `propose_term_update`: proposes a term update.
- `propose_timeline_event`: proposes a timeline event.

Proposal tools cannot write files. The author must accept text blocks or data proposals in the chat panel. Chapter proposals store a SHA-256 hash of the source text, stop when the chapter has changed, create a chapter-history snapshot, and can be rolled back from the chat panel.

## Long-term memory

After a confirmed chapter write, the Agent creates a chapter memory under:

```text
.inkforge/agents/memory/<chapter-id>.json
```

Memories include a summary, character states, unresolved threads, clue updates, world changes and retrieval keywords. Tool results also attach source references to the final assistant response.

Older chapter memories are compacted into:

```text
.inkforge/agents/memory/project-digest.json
```

Before each model turn, InkForge builds a bounded automatic context containing the current chapter tail, recent memories, the compressed older-memory digest and the highest-scoring semantic hits. The trace records the budget, estimated usage, included hits and omitted items.

The local semantic index is stored at:

```text
.inkforge/agents/index/semantic-index.json
```

It uses deterministic multilingual hashed vectors and lexical boosting, so retrieval remains local and does not require an embedding API.

## Multi-Agent workflow

The full chapter workflow runs these stages with an author checkpoint between each one:

```text
Context researcher
  -> Planning Agent
  -> Drafting Agent
  -> Review Agent
  -> Revision Agent
  -> Memory Agent
  -> Confirm write
```

Stages can be continued, skipped, retried after failure, paused or cancelled. Scene plans are stored in `.inkforge/scene-plans/` rather than only in browser storage.

### Literary polish workflow

The `literary-polish` preset keeps three inspectable drafts:

```text
Fact-locked context
  -> rough, information-complete draft
  -> selective non-visual sensory pass
  -> independent editor rhythm pass
  -> author confirmation
  -> chapter write
```

The editor pass can use the optional editor model from Provider settings. If it is blank, the main model is reused.

### Agent room and mentions

Each project stores an extensible member roster in `.inkforge/agent-extensions.json`. Built-in members are `@导演`, `@作家`, `@编辑` and `@资料员`. Every member has its own role prompt, optional model override and tool allow-list.

A single mention starts that member directly. Multiple mentions or `@全体` create a persistent collaboration run:

```text
Coordinator delegates tasks
  -> specialists run independent model sessions
  -> each specialist may call only its allowed read tools
  -> results are handed to the coordinator
  -> coordinator resolves disagreements and owns proposal writes
  -> editor or coordinator may request one bounded rework
```

Collaboration runs, tasks, private transcripts, per-Agent working memories, handoffs, reviews and bounded rework state are stored inside the chapter chat session. A later run seeds each Agent with its own recent memory rather than sharing one synthetic group persona. Failed full-chapter runs also keep their collaboration state alongside scene checkpoints, so retry resumes the unfinished specialist task.

The chat renders every specialist response separately and provides an expandable collaboration card for task status, permissions, results and Agent-to-Agent messages.

## Provider compatibility

The provider must expose an OpenAI-compatible `/chat/completions` endpoint with streaming SSE, `tools` and `tool_calls` support. Streaming tool-call fragments are assembled by index before execution. A provider that only supports plain text completions can still use the existing single-task AI actions, but cannot run the chat Agent loop.

## Safety boundary

- The renderer has no Node.js or direct filesystem access.
- Tool arguments are parsed as data and never executed.
- Paths are resolved through `FileRepository.assertInsideProject`.
- Project text is treated as untrusted novel content, not system instructions.
- Agent loops stop after six model turns.
- A chapter allows only one active Agent or write operation.
- Provider requests time out after 90 seconds and retry transient 429/502/503/504 failures once.
- Chapter changes remain pending until explicit author confirmation.
