# 600–700 万字未完结小说续写改造设计

## 1. 目标与边界

本改造的目标不是“把更多正文塞进一次提示词”，而是把 InkForge 从通用写作辅助工具升级为一个可审计、可恢复、可长期运行的续写工程系统。

目标场景：

- 已有正文约 600–700 万中文字符，常见规模为 1000–2500 章。
- 需要继续创作数十万到数百万字，而不是只续一两章。
- 必须保持人物、能力体系、时间线、地理、称谓、叙述视角和角色口吻的一致。
- 必须识别已有伏笔、悬念、承诺和未完成角色弧，并制定回收计划。
- AI 只能生成带证据、可审阅、可回滚的提案，不能把推测自动升级为事实。

明确不承诺：

- 不声称模型可以仅凭一次全书分析就“完全理解”700 万字。
- 不保证自动抽取结果百分之百正确；低置信度和冲突信息必须进入人工确认队列。
- 不把“相似句式”当作“文风一致”。文风要拆成可观测指标、角色口吻和场景范例分别控制。
- 不自动续写几百章后一次性交付。长期生产必须按场景、章节、剧情弧设置检查点。

## 2. 当前实现与实际需求的差距

项目已有本地章节、资料库、伏笔、时间线、语义检索、章节记忆、分支草稿和人工确认机制，这些可以复用。但当前实现的规模基线和续写闭环不足。

| 当前能力   | 当前做法                                                               | 700 万字场景的问题                                                     |
| ---------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 文稿导入   | Renderer 用 `FileReader` 读取完整文件，再把全部章节正文放入 React 状态 | 大文件占用多份内存，界面容易冻结；无断点、编码探测、重复检测和失败恢复 |
| 语义索引   | 每次查询先读取所有章节和资料，重算全库指纹                             | 查询成本随全书线性增长；改单章也会触发全量重建判断                     |
| 检索粒度   | 一章一个文档，最多保留前 20,000 字符                                   | 长章后半段不可检索；命中结果无法精确指向场景和段落                     |
| 语义表示   | 384 维哈希词袋                                                         | 对别称、隐含关系、相似事件和跨章节伏笔的语义召回能力有限               |
| 长期记忆   | 最近 4 章 + 更早章节摘要拼接后截取 5,000 字符                          | 早期事实被位置截断；没有按人物、状态、时间和剧情线定向取回             |
| 上下文构建 | 固定优先级、固定条数，默认约 1,800 token                               | 先出现的资料容易挤掉真正相关资料；没有硬事实与软参考的区别             |
| 批量续写   | 当前章末尾 12,000 字符 + 人物名 + 世界观引用 + 一条 style              | 看不到跨卷因果、当前人物状态、待回收伏笔和相似场景范例                 |
| 伏笔模型   | 单个埋设章节、一个预期回收文本、一个状态                               | 无多次推进、假线索、依赖关系、回收窗口、证据位置和误判处理             |
| 文风       | 项目级自由文本 + 人物 `voiceNotes`                                     | 无统计基线、叙述者画像、角色对白样本、场景分类和漂移检测               |
| 质量检查   | 以章节级规则检查和通用模型复核为主                                     | 缺少基于全书证据的硬事实校验、状态转换校验和伏笔闭环校验               |
| 性能验证   | 已验证约 280 万字 / 400 章                                             | 尚未覆盖 700 万字、2000 章、长时间断点任务和增量更新                   |

因此，现有能力适合作为 UI 和安全底座，但不应直接把现有 `BatchProductionService` 扩大批次数量来解决问题。

## 3. 核心设计原则

### 3.1 三层事实来源

把数据严格分为三层，避免“模型猜测污染原著设定”。

1. **原始证据层**
   - 原章节 Markdown/TXT。
   - 内容哈希、章节顺序、段落/场景偏移。
   - 永远不由分析任务改写。

2. **作者确认的正典层**
   - 人物、地点、物品、能力、关系、时间线、剧情线、伏笔。
   - 每条事实都有稳定 ID、有效章节区间和证据引用。
   - `author_locked` 事实是续写的硬约束。

3. **可重建派生层**
   - 全文索引、向量、自动摘要、候选事实、风格统计、缓存。
   - 放入 `.inkforge/continuation/`，可删除后重建。
   - 模型输出默认只能进入此层或待确认队列。

### 3.2 正典不是静态百科，而是带时间的状态变化

“林昭在青州”与“林昭在京城”可能都正确，只是发生在不同章节。事实模型必须包含有效区间和变化原因，不能只保留一个 `currentState`。

### 3.3 检索必须由任务驱动

续写一个谈判场景、检查某个伏笔、核对战力体系，需要的资料不同。系统先生成检索计划，再组合：

- 强制包含的锁定事实；
- 前一场景和上一章的即时连续性；
- 当前剧情弧、章节目标和场景计划；
- 参与人物的当前状态与角色口吻；
- 到期或相关的未决剧情线；
- 全文关键词/语义命中；
- 与当前场景类型相似的原文风格范例。

### 3.4 所有结论都要能回到原文

摘要、人物状态、伏笔和冲突事实都保存 `EvidenceRef`。用户应能从任何结论一键跳到原文章节和偏移位置。

## 4. 目标架构

```text
大文件/文件夹
  -> CorpusImportService（流式拆章、编码探测、断点、哈希）
  -> 原始章节 Markdown（现有项目格式）
  -> AnalysisJobService（可暂停、可恢复、按内容哈希增量）
       -> 场景切分 / 章节摘要 / 实体候选 / 事件 / 状态变化 / 伏笔候选
       -> Canon Inbox（人工确认、合并、驳回）
  -> CanonStore（作者确认事实 + 证据 + 有效区间）
  -> ChunkIndexService（FTS + 可选真实 embedding + 元数据过滤）
  -> StoryMemoryService（场景/章节/剧情弧/卷/全书分层记忆）
  -> ContextCompiler（按任务组装有来源、有预算的证据包）
  -> ContinuationOrchestrator
       章节契约 -> 场景计划 -> 场景草稿 -> 硬规则检查
       -> 连续性/伏笔/文风复核 -> 定点修复 -> 分支提案
  -> 作者确认
  -> 正文、状态、索引和记忆的原子更新
```

### 4.1 存储策略

继续使用 Markdown 作为正文事实来源，不把正文搬入数据库。

建议新增：

```text
canon/                                  # 可选纳入作品版本控制
  entities/*.json
  facts.jsonl
  state-transitions.jsonl
  story-threads/*.json
  style-profile.json

.inkforge/continuation/                 # 可重建派生数据
  manifest.json
  index.sqlite                          # FTS、chunk 元数据、任务状态
  embeddings.bin                       # 或 SQLite BLOB；按 provider/model 分代
  jobs/*.json
  candidates/*.jsonl
  memories/
    scenes/
    chapters/
    arcs/
    volumes/
    global.json
  reports/
```

索引层建议抽象为 `DerivedStore`。优先验证 Electron 运行时自带 SQLite 能力，避免直接引入需要原生重编译的依赖；若运行时不满足，再选择可打包的纯 JS/WASM 方案。这样不会破坏当前 `npmRebuild: false` 的发布策略。

## 5. 关键数据模型

### 5.1 证据

```ts
interface EvidenceRef {
  chapterId: string;
  sceneId?: string;
  startOffset: number;
  endOffset: number;
  excerpt: string;
  contentHash: string;
}
```

偏移在正文变化后使用“内容哈希 + 引文 + 邻近位置”重定位，复用现有批注锚点的思路。

### 5.2 带时态的事实

```ts
interface CanonFact {
  id: string;
  subjectId: string;
  predicate: string;
  objectValue: string | number | boolean | string[];
  validFromChapterId?: string;
  validToChapterId?: string;
  certainty: number;
  status: "candidate" | "confirmed" | "author_locked" | "conflicted" | "rejected";
  evidence: EvidenceRef[];
  supersedes?: string[];
}
```

典型谓词包括 `located_at`、`knows_secret`、`power_level`、`owns_item`、`relationship`、`alive`、`injury`、`goal`。涉及续写的当前状态通过按章节顺序重放状态变化得到，而不是覆盖历史。

### 5.3 剧情线与伏笔

把现有单一 `Clue` 扩展为 `StoryThread`：

```ts
interface StoryThread {
  id: string;
  type: "foreshadowing" | "mystery" | "promise" | "character_arc" | "conflict" | "world_question";
  title: string;
  status: "candidate" | "active" | "progressing" | "due" | "resolved" | "abandoned";
  setupRefs: EvidenceRef[];
  progressRefs: EvidenceRef[];
  payoffRefs: EvidenceRef[];
  expectedPayoff?: string;
  earliestPayoffChapter?: number;
  latestPayoffChapter?: number;
  dependencies: string[];
  relatedEntityIds: string[];
  confidence: number;
  locked: boolean;
}
```

这样可以表达“一次埋设、多次推进、最终回收”，也能区分真正的伏笔、普通信息和模型误判。

### 5.4 风格画像

风格画像不只保存形容词，至少包括：

- 叙述视角、焦点人物切换规则、时态；
- 句长分布、段长分布、对白占比、动作/心理/环境描写占比；
- 标点、连接词、成语、口头禅和高频搭配；
- 章首方式、章尾钩子类型、信息揭示速度；
- 每个主要人物的称谓习惯、句长、语气词、礼貌度、攻击性和禁用表达；
- 按场景类型保存原文范例引用，如战斗、对白、悬疑揭示、日常、感情、转场；
- 作者明确的禁用模式，例如过度总结、连续反问、模板化排比或现代网络词。

数值指标由本地算法稳定计算；叙述策略和角色口吻由模型提取后经作者确认。

## 6. “小说考古”初始化流程

700 万字项目第一次打开时不应直接进入续写，而应进入一次可恢复的建档流程。

### 阶段 A：流式导入

- 在 Electron 主进程按流读取，Renderer 只接收进度和抽样预览。
- 探测 UTF-8、UTF-8 BOM、GB18030 等常见编码；低置信度时让用户确认。
- 支持单文件、按章文件夹、按卷目录。
- 章节标题识别规则可预览和修正；保留原文件路径、原顺序和内容哈希。
- 每完成一章即落盘并记录 checkpoint；重启后只继续未完成部分。
- 重复章节以哈希和标题相似度提示，不静默覆盖。

### 阶段 B：确定性预处理

- 段落和场景切分；
- 人名、称谓、地点、术语候选统计；
- 引号对白归属候选；
- 字数、句长、段长、对白占比等风格统计；
- 章节级倒排索引；
- 不调用模型也能完成，成本为零。

### 阶段 C：分章结构化抽取

对每章生成严格 JSON：

- 章节摘要与场景摘要；
- 出场实体和别称；
- 事件、地点、相对时间；
- 人物进入状态、离开状态和发生原因；
- 新事实、被否定事实、冲突事实；
- 伏笔/悬念/承诺的埋设、推进、回收候选；
- 角色口吻样本；
- 所有字段附原文证据偏移和置信度。

模型输出解析失败时只重试该章，不重跑全书。抽取器、提示词、模型和版本都写入产物元数据，升级后可以只重建受影响部分。

### 阶段 D：跨章归并

- 合并同一人物的本名、别称、称号和误写候选；
- 按事件顺序构建状态转换；
- 发现“同一时点两地出现”“已失去物品却继续使用”等冲突；
- 聚合跨章剧情线；
- 生成卷级、剧情弧级和全书级摘要。

### 阶段 E：Canon Inbox

用户按影响范围审阅，而不是逐条审完全部候选：

1. 先确认主角、核心配角、力量体系、主要地点和主线。
2. 再确认高风险冲突和到期伏笔。
3. 低频背景实体可保持 `candidate`，需要时再确认。

系统必须支持批量合并别称、批量接受同类低风险事实、跳转证据和撤销。

## 7. 分层记忆与混合检索

### 7.1 分层记忆

每层保存不同信息，不能用一个不断增长的全书摘要替代：

| 层级   | 主要内容                                         | 更新时机             |
| ------ | ------------------------------------------------ | -------------------- |
| 场景   | 场景目标、冲突、参与者、进入/离开状态、信息增量  | 场景确认后           |
| 章节   | 本章因果链、人物决定、状态变化、伏笔变化、承接点 | 章节确认后           |
| 剧情弧 | 弧目标、关键节点、未完成承诺、节奏和转折         | 每 5–20 章或人工调整 |
| 分卷   | 卷级因果、主要矛盾、角色阶段、遗留问题           | 卷结束或重算         |
| 全书   | 核心前提、硬规则、主线现状、结局约束             | 正典变化后增量更新   |

### 7.2 Chunk 索引

- 按场景优先切块；无法识别场景时按约 600–1200 中文字符切块，并保留少量重叠。
- Chunk 元数据包含章节、卷、场景、参与人物、地点、剧情线、时间范围、原文偏移和哈希。
- FTS 用于名称、术语和原句精确召回。
- embedding 用于隐含关系和相似情境召回；没有 embedding provider 时明确标记为“词法检索”，不能伪装成语义检索。
- 改一章只删除并重建该章 chunk，不重新读取和序列化全书。
- 向量模型变化时建立新 generation，成功后原子切换。

700 万字按约 800 字一个 chunk，规模大约是一万级 chunk，不需要一开始引入独立向量数据库。带元数据过滤的本地线性/分块扫描已经可用，后续再根据实测增加 ANN。

### 7.3 ContextCompiler

每次续写生成结构化 `EvidencePack`：

```ts
interface EvidencePack {
  hardConstraints: CanonFact[];
  immediateContinuity: EvidenceRef[];
  chapterContract: ChapterContract;
  activeCharacterStates: CanonFact[];
  dueThreads: StoryThread[];
  retrievedEvidence: EvidenceRef[];
  styleExemplars: EvidenceRef[];
  exclusions: string[];
  tokenUsageBySection: Record<string, number>;
}
```

优先级不是简单的固定列表，而是：

1. 当前任务涉及的 `author_locked` 事实，无条件包含；
2. 当前场景进入状态和上一场景离开状态；
3. 作者本章契约；
4. 当前人物、地点、能力和物品的有效事实；
5. 已到回收窗口或与本章相关的剧情线；
6. 混合检索结果；
7. 同类场景风格范例。

超预算时先压缩低置信度背景，不得裁掉硬约束，并在 UI 明示哪些资料被省略。

## 8. 续写生产闭环

### 8.1 先制定“续写契约”

正式写正文前，作者确认：

- 预计还要写多少卷/章/字；
- 目标结局和不能改变的结局约束；
- 主线、支线、角色弧的剩余目标；
- 必须回收、可放弃、刻意保持开放的剧情线；
- 节奏上限，例如一个大伏笔不能连续三章强推；
- 内容边界和禁写项。

这一步解决“会写，但越写越偏”的问题。

### 8.2 以场景为最小生成单元

推荐流水线：

1. **章节合同**：本章必须发生、不得发生、进入状态、离开状态、需要推进的剧情线。
2. **场景计划**：每个场景的 POV、地点、参与者、目标、冲突、信息增量、结束状态。
3. **证据包编译**：按场景实时取回正典、原文和风格范例。
4. **场景草稿**：每次生成约 800–1500 字，避免整章一次生成后的大面积漂移。
5. **硬校验**：锁定事实、称谓、时间、地点、人物状态、能力代价、物品归属。
6. **软校验**：角色口吻、文风漂移、节奏、重复表达、过度解释、章尾钩子。
7. **定点修复**：只重写失败段落，保留通过的内容。
8. **分支提案**：显示正文差异、引用证据、风险和评分。
9. **作者确认**：确认后原子更新正文、记忆、状态转换、剧情线和索引。

### 8.3 检查器分级

硬失败：

- 违反作者锁定事实；
- 没有过渡就发生不可能的地点/生死/物品/能力状态变化；
- 时间线倒置；
- 使用尚未获得的知识；
- 已确认的专名或能力规则错误。

软警告：

- 角色语气偏移；
- 句长、对白比或段落密度显著漂移；
- 与近期章节重复桥段或表达；
- 伏笔推进过密、长期无推进或过早回收；
- 节奏与本章合同不符。

硬失败不能自动进入“可应用”状态；软警告允许作者带风险接受。

## 9. UI 改造

在现有导航上新增一个“续写工程”入口，内部包含：

1. **建档中心**
   - 导入、拆章预览、编码、断点进度、失败重试、预计模型成本。

2. **正典收件箱**
   - 候选事实、实体归并、冲突、证据跳转、置信度和批量确认。

3. **剧情线雷达**
   - 活跃/到期/已解决剧情线，埋设—推进—回收时间轴，依赖图和本章候选。

4. **风格实验室**
   - 全书、分卷、角色和场景类型画像；选择代表性原文；设置允许漂移范围和禁用模式。

5. **续写控制台**
   - 续写契约、章节合同、场景计划、证据包预览、生成、检查和差异确认。

6. **一致性中心**
   - 硬冲突、软警告、依据原文、接受例外、修正正典或重写正文。

现有修订工作台、分支、历史版本、Agent 提案和备份中心继续复用。

## 10. 对现有代码的改造映射

| 现有模块                       | 改造方向                                                                  |

| `SemanticIndexService.ts`      | 拆为 `ChunkIndexService`、`EmbeddingService`、`HybridRetriever`，增量索引 |

需要新增的主进程服务：

- `CorpusImportService`

## 11. 分阶段实施顺序

以下是工程里程碑，不是固定日历承诺。

### P0：建立真实规模基线

- 把性能探针参数化为 500/1000/2000 章、700 万字。
- 记录导入、打开、搜索、索引、全书巡检、备份的时间和峰值内存。
- 准备一套脱敏或合成的“金标准事实/伏笔/状态变化”测试集。

完成标准：能稳定复现当前瓶颈，并且后续每阶段都有回归数字。

### P1：流式导入与持久任务

- 主进程流式拆章、编码探测、哈希、断点和重试。
- `AnalysisJobService` 支持暂停、取消、重启恢复和按章节增量执行。
- Renderer 不持有全书正文数组。

完成标准：700 万字导入不中断 UI；进程被关闭后能够从最后一个完整章节继续。

### P2：Chunk 索引与证据体系

- 场景/段落 chunk、FTS、可选真实 embedding、增量更新。
- 所有命中带章节偏移，可跳回原文。
- 检索评估使用金标准 query，不只看主观示例。

完成标准：单章修改不触发全库重建；金标准事实在 top-20 中的召回率达到约定阈值。

### P3：正典、状态和剧情线

- `EvidenceRef`、`CanonFact`、`StateTransition`、`StoryThread`。
- 分章抽取、跨章实体归并、冲突发现、Canon Inbox。
- 从现有人物/世界观/时间线/伏笔 JSON 迁移并保留回滚点。

完成标准：主角和核心剧情线可以从结论跳回证据；冲突事实不会被静默覆盖。

### P4：风格画像与 ContextCompiler

- 本地风格统计、角色口吻样本、场景范例库。
- 任务感知上下文、硬约束保留、预算可视化。
- 上下文快照写入运行追踪，后续可复现。

完成标准：任何一次草稿都能回答“用了哪些设定和原文范例、为什么使用、哪些资料被省略”。

### P5：场景级续写闭环

- 续写契约、章节合同、场景计划。
- 场景生成、硬/软检查、定点修复、分支提案。
- 作者确认后原子更新正文、正典候选、记忆和索引。

完成标准：硬冲突阻止应用；软风险可见；失败可恢复；已通过段落不因局部问题被整章重写。

### P6：长期生产验证

- 连续生成并人工审阅至少 30–50 章的试运行。
- 观察风格漂移、伏笔召回、重复桥段、成本和人工修改率。
- 再决定是否扩大自动批次，而不是预先追求“无人值守”。

## 12. 建议验收指标

指标应在 P0 用真实机器和真实章节分布校准，以下作为初始建议：

- 700 万字 / 2000 章流式导入期间界面可操作，任务可断点续跑。
- 单章修改后，只重建该章相关 chunk、摘要和派生状态。
- 常规检索不读取全部章节正文；一万级 chunk 的本地检索 P95 小于 1 秒。
- 金标准人物状态、能力规则、地点和伏笔查询的 top-20 证据召回率不低于 95%。
- 涉及当前场景实体的 `author_locked` 事实进入上下文的覆盖率为 100%。
- 测试集内违反锁定事实的草稿 100% 被硬检查拦截。
- 所有自动抽取事实都有证据；无证据结论不能转为 `confirmed`。
- 对已确认正文，任意一步都能从章节历史和任务 checkpoint 恢复。
- 记录每章生成后的人工改写比例、被拒绝率和每千字成本，用它们判断产品价值，而不是只看模型评分。

## 13. MVP 取舍

第一版应该优先完成：

1. 流式导入和断点分析；
2. Chunk/FTS 索引和证据跳转；
3. 作者确认的核心正典；
4. 多阶段伏笔/剧情线台账；
5. 风格画像和代表性范例；
6. 场景级“计划—生成—校验—提案”闭环。

可以后置：

- 独立向量数据库和复杂 ANN；
- 多 Agent 自主协作；
- 一次批量生成几十章；
- 互动叙事/Twine/Ink 方向；
- 更丰富的出版和社区能力。

这个需求的产品护城河不是“Agent 数量”，而是长期记忆的可信度、证据可追溯性、伏笔闭环和作者可控性。

## 14. 最终建议

项目现有的本地优先、提案确认、分支、历史、备份和资料库方向是正确的，不需要推倒重来。真正需要重做的是输入规模、派生知识、上下文编译和续写生产链。

最合理的切入点是先完成 P0–P2：让 700 万字能够安全导入、增量索引，并让每次检索都能精确回到原文。只有证据底座可靠之后，人物状态、伏笔、文风和自动续写才有可信的上层闭环。
