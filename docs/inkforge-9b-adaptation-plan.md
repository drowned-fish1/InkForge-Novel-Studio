# InkForge 专用写手适配方案

日期：2026-10-10。共享写手协议、逻辑编辑与独立复核、项目资料历史与接受正文后的抽取、三流程对照工具和项目级 YOLO 已实现。模型质量仍须部署后实测。本文不变更训练会话的脚本、数据、权重或运行任务。

## 判断依据

目前有 CPT 文风收益的观察，但 Base/CPT 与官方 9B 指令版的局部对照仍出现归属、资源账目、能力和重复错误。两道题不能代表整体能力，也不足以证明增加上下文、降低温度、换推理实现或扩大模型能解决这些错误。

两段保留文风的逻辑编辑由主助手完成，属于方案示范，尚未证明某个部署中的外部编辑模型能稳定达到相同效果。因此首个产品目标是可复核的「专用写手草稿 → 事实编辑 → 复核 → 作者确认」。

## 建议的最小生产流程

1. 规划连接提出本场景目标、进入状态、拟发生的事件和期望结束状态。它们必须区分历史事实与创作计划，计划不能改变已确认事实。
2. 从本书独立的 `project-data.json` 按相关性、故事位置和预算选择完整栏目，结合当前章及上一章末尾编译上下文快照。每本书自行组织数据，没有通用场景包或必填小说字段。
3. writer 用共享协议生成当前场景正文。初始可尝试每场 800–1500 中文字，这只是待测试的起点，不是已验证最优长度。
4. reviewer 接收相同资料快照、前文、计划和写手草稿，检查资源、归属、人物知识、能力及因果，返回实际修订正文、发现、修改依据和未决问题。
5. 独立请求再次对照同一快照复核修订正文，不提供编辑自评作为结论依据。未明确通过、仍有硬矛盾或未决问题时阻止应用，保留草稿。模型复核是语义评估，不能视为确定性正确证明。
6. 草稿和修订稿分开保存，生成可审阅提案。作者接受后，以版本检查和可恢复提交更新正文、状态、记忆及索引。后续场景只能依赖明确接受的版本；如支持连续批量草拟，则使用隔离的临时分支状态。

默认试验先让每场接受一次逻辑审核，积累问题分布后再考虑低风险场景跳过编辑。编辑预算耗尽、模型失败或仍有硬矛盾时进入 blocked/review 状态，保留草稿供查看。可以重试或人工选择，但不能因为草稿更像目标文风就自动放行。

## 项目专属资料（已实现）

每本小说保存自己的 `project-data.json`。它是一份项目数据记录，栏目名和栏目内容均由本书决定；不预设共同的货币、装备、蛊虫、技能或系统字段，也不要求作者填通用场景表。`entries[].content` 接受任意 JSON，栏目建议按具体人物、物品或规则拆分，便于小模型按需读取。

项目内 Agent 有两个工具：

- `get_project_data`：读取本书资料及版本。支持指定栏目、查询排序和目录分页，不会读取其他项目。
- `propose_project_data_update`：以读取时的版本为基础，新建/替换/删除选定栏目。普通模式由作者接受后写入；YOLO 自动应用本轮新提案。版本冲突仍要求重新读取。

初版由项目 Agent 根据作者要求、已有设定和正文提出，不自动填造缺失内容。以后可以直接要求 Agent 修改或删除某一栏目。既有角色卡、正典和大纲仍各自负责原来的功能；专属资料补充本书独有的信息，冲突时需回到正文和作者确认，不将模型草稿当成既成事实。

数据按版本保存，写入串行化并使用原子替换。新项目创建空文档，旧项目在首次接受资料提案时创建。项目备份携带这份数据并显示其变化。默认导演、资料员可以提议更新，作家和编辑可以读取；旧项目仅为未改动的内置权限表补上新工具，作者自定义权限保留。

Agent 自动上下文、普通正文/审阅请求、续写 EvidencePack，以及训练共用的 writer 消息构建器已经接入专属资料。按查询相关性和预算选取完整栏目，超限栏目省略而非截断 JSON。每次更新保存 before/after、发生章节及可选原句证据，读取旧章节时倒序撤销后续章节变化；带偏移证据的同章变化也受截止点约束。历史工具支持分页；作者自由修改但不标章节或依据的数据无法精确重放故事时间。源正文重写后，已有记录的语义有效性仍须重新核对，哈希检查用于提案应用时拒绝过期来源。

9B 写手使用运行时传入的本书资料，不需要把每本书的数据重新训练进权重。工具调用由 Agent 连接承担。正文接受后，可选资料维护 Agent 从已接受正文生成更新；每项变化必须引用实际原句并验证全文哈希和 UTF-16 偏移，普通模式留下候选，YOLO 自动应用。引用匹配不保证抽取语义正确。更新失败保留已接受正文并提示重试；正文索引自动增量更新。

## 编辑契约

编辑输入中的事实权威顺序为：作者锁定且在当前故事位置有效的正典、已确认前文状态、可引用原文证据；创作计划是目标，9B 草稿中的新增内容是候选。冲突证据进入待确认队列，禁止编辑模型静默裁决。

默认要求保留不造成矛盾的原句、视角、人物称谓、对白习惯和段落节奏。发现局部错误时只修对应段落；因果链严重损坏时明确标为局部重写。必须改变作者目标或锁定事实时请求作者处理，不自行放宽约束。

建议编辑结果包含 `revisedText`、`findings`、`changes`、`proposedStateTransitions`、`unresolvedIssues`。发现记录应包含正文位置、对应 fact/evidence ID、原因与严重度；修改记录保存旧段落哈希，应用时拒绝过期定位。

界面展示原稿/修订稿、修改原因、段落差异、事实变化和未解决问题。原句保留率、篇幅、对白比例、段落与句长分布用于观察文风漂移，不能作为「必须保留错误」的硬门禁。词汇重复与风格相似也不能代替作者判断。

## 账目示例

已确认：陆砚有 12 块元石。交易支出为 7 块，无其他收入，则余额为 5。若草稿写余额 8，编辑应修正文或指出交易条件冲突，而非凭空新增 3 块收入以解释原稿。

已确认：木匣为空，引潮蛊在左袖。草稿写「从匣内取蛊」时，除非正文有合法转移过程，应修正归属描写；不能为保留原句再增加一只蛊。

确定性规则能检查输入与经审阅的结构化账目，但任意小说正文中的交易、比喻、谎言和条件句仍需语义判断，不能宣称用数字正则就可完成逻辑验证。

## 训练与运行时协同

- 将 `inkforge.writer.v1` 的结构与渲染版本冻结为明确工件，训练导出与应用调用共用代码；完整编码再固定 tokenizer、官方聊天模板、assistant 边界和结束符。
- 验证相同任务在两端产生相同 messages，并核对部署侧实际输入的 token 序列与停止设置。共享函数本身不保证服务端聊天模板相同。
- 应用场景状态字段要与训练中能可靠获得的字段对齐；缺失值明确未知。反向标注中的目标段信息不得伪装成此前已知事实。
- 先保留 4K 可比基线。上下文预算计入最终消息、模板与输出预留，硬事实过多时拆场景；8K/16K 必须有相应训练与验收，不能靠推理参数视为已经适配。
- 9B 首先专用于正文；工具调用、规划 JSON 与事实抽取分别评测，不能从正文 SFT 推定这些能力已掌握。
- 作者接受的修改可作为待审候选训练数据，不能直接在线训练。保留来源与许可、输入快照、拒绝原因，严格隔离训练/验证/测试。偏好训练应在已有可靠 SFT 与配对评测后再研究。

## 实施顺序与验收

**P0：统一写作输入和前文。** 应用接 `buildWriterMessages`，补当前章末尾、历史截止过滤、真实输入预算与停止符验收。用一个固定任务证明训练与应用协议一致。

**P1：打通双模型逻辑编辑。** 在续写编排中实现草稿 → 编辑 → 再检查 → 分支提案，修复创作组的错误数字保留与自动退回原稿规则。用盐窟和黑市题作为固定回归，但不能只针对这两题调优。

**P2：项目专属资料与修改依据。** 已实现独立 JSON 数据、Agent 读写提案、差异预览、删改及上下文接入。已补来源证据展示、状态历史与正文接受后的候选更新；结构化账目/归属检查按作品设计，不作为所有项目的前置条件。

**P3：质量、成本与长期生产。** 比较 writer 单独输出、writer＋编辑、通用大模型单独写三条流程；同题控制事实包、场景目标与采样条件，记录模型/template 版本。分别评估硬矛盾、目标完成、重复、原作专名串入、文风偏移、作者接受率、延迟、Token 和实收成本。

首批可准备 30–50 个独立场景作为工程筛查集，覆盖账目、归属、人物知识、实力限制、时间与承诺；这是建议规模，不是统计置信度保证。最终检验连续多场景/多章运行和状态重放，避免单场景正确、后续仍累积错误。

工作优先级是让文风收益转化为作者愿意接受的修订正文。大模型整段重写过多、成本高于直接用大模型写或持续破坏文风时，要根据对照结果调整路线，而非因为已经训练了 9B 就固定使用它。
